# MPPI GPU 이식 설계 v3: CUDA C++와 ctypes

작성일: 2026-11-25. 범위는 설계와 합성 커널 실측이다. 제어기 본 구현과 시뮬레이션은 하지 않았다. 기존 설계 `2026-11-25-gpu-port-design.md`를 토대로 지시서의 CUDA C++ 전제를 반영했다.

## 먼저 확인할 사항과 결론

| 항목 | 내용 |
|---|---|
| 사용자 확인 | GPU 초기화·실행 오류나 시간 초과 시 검증된 정지 경로로 주행을 중단하는 안을 제안한다. 검증된 CPU 고정 설정을 별도 선택할지 결정이 필요하다. 실행 중 자동 전환은 하지 않는다. |
| FP32 | FP64가 늦을 때 검토한다. FP32 허용 오차, 명령 및 shield 불일치 허용 기준은 아직 승인되지 않았다. |
| 폐루프 | 비교할 36개 조건과 성공·충돌·정지 기준을 주행 전에 확정해야 한다. 이 보고서는 주행 실행 승인이 아니다. |
| 전망 | RTX 3060의 축약 커널은 B=4,096에서 가능성을 보이지만 전체 p99 15 ms 달성은 미확인이다. C=16,384는 CPU 샘플 부분만 선형 추정해도 약 18 ms라 S1의 목표 달성이 어려울 가능성이 크다. 실측이 아니며 S2를 검토할 근거다. |
| 큰 위험 | 실제 ST·투영·장애물·TTC 비용, CPU 가중평균, 콜백, 동기화, OS 지연은 이번 축약 실험과 다르다. 4090 결과도 없다. |

## 단계별 구현 계획과 후퇴 지점

아래 소요 시간은 구현자 한 명의 대략적인 작업 시간이며 환경·오차 문제에 따라 늘어난다. 이 계획은 이번 구현 허가가 아니다.

|---|---:|---|---|
| 0. 환경 재현 | 1–3시간 | 3060과 평가 4090에서 빌드, 로드, warmup, 결과 확인 및 동일 스크립트 실측 | 실패 단계 기록, GPU 경로 중지 |
| 1. S1 FP64 및 비용 동등성 | 1–3일 | 고정 후보 주입, 모든 후보 총비용 절대차 최대 1e-9 이하, 비유한 값·분기 비교 | 분리 경로로 항별 추적; 통과 전 다음 단계 금지 |
| 2. 명령 동등성 | 0.5–2일 | 동일 내부 상태와 후보를 주입한 2,000스텝 명령 비교; 일치 의미와 허용 오차 사전 확정 | 불일치 원인 수정 또는 CPU 기준으로 후퇴 |

| FP32 검토 | 추가 1–3일 | FP64 부족 시 동일 입력 비용·순위·조향·가속·속도·shield 차이를 분석하고 별도 승인된 기준 통과 | 미승인 또는 위반 시 FP32 채택하지 않음 |
| CPU의 C++ 이전 | 별도 산정 | GPU 검증 이후 남은 CPU 병목과 동등성 확인 | 이전하지 않고 기존 CPU 코드 유지 |

## 실험 조건과 방법

기존 `crazy_shamir` 컨테이너, RTX 3060(sm_86), WSL2, CUDA Toolkit nvcc 12.4.131, 드라이버 표시 610.88. `curand_kernel.h` 및 libcurand가 존재하며 프로토타입은 헤더 기반 Philox를 사용한다. Numba CUDA는 사용하지 않았다. `misys:forza_full`의 nvcc 존재는 지시서에 기록된 이전 확인이며 이번에는 실행 중인 컨테이너에서만 재확인했다. 신규 패키지를 설치하지 않았다.

커널은 후보당 한 스레드, 30스텝과 스텝당 두 substep, 트랙 후보 16점 탐색, 장애물 0/4/5개 비용을 계산한다. 제로 입력, 합성 트랙 및 단순한 동역학·거리 비용이다. **실제 ST 방정식, 투영 힌트와 이동 장애물·TTC 등 전체 비용과 동등하지 않다.** 동일 후보의 양 정밀도 결과가 유한·양수이고 반복 후보가 같은지 확인했으나 실제 CPU 정답 비교는 하지 않았다. FP32/FP64는 템플릿 형식으로 별도 컴파일했으며 PTX의 모든 연산 형식과 레지스터 사용량은 따로 분석하지 않았다.

각 항목은 100회 워밍업 후 1,000회다. 커널·복사는 동기화된 CUDA 이벤트 시간, ctypes는 빈 함수 왕복의 CPU wall time이다. 복사의 pageable 경로는 호스트 staging 및 Python 호출 시간이 이벤트 밖에 있을 수 있어 실제 전체 복사 시간의 하한에 가깝다. pinned 버퍼 충전 비용도 빠진다. H2D는 K×30×2, D2H는 K개 값이다. 최초 init은 컨텍스트 생성, 이벤트·장치 메모리·pinned 메모리 할당과 장치 입력 초기화 호출을 포함하므로 순수 컨텍스트 시간은 아니다. 최초 커널 wall에는 로드와 동기화가 포함된다. 여러 수치의 p99를 합한 것은 실제 전체 p99가 아니다. 측정 중 GPU 공유 부하와 클럭을 통제하지 않았다.

## 15 ms 가능성 판단

기존 오프라인 벤치마크에서 지시서가 제공한 `sample_ms` 평균은 K=1,024/2,048/4,096/8,192에서 1.0/2.6/5.2/9.0 ms다. 코드에서 `sample_ms`는 샘플링·후보 조립 등을 포함하고 가중평균은 별도 `update_ms`다. 따라서 5.2 ms에 가중평균이 포함됐다고 보면 안 된다. 실험 조건과 통계가 다른 CPU 평균과 GPU p99를 더하는 아래 값은 예산 감각용 지표이며 전체 p99 예측치가 아니다.

- K=4,096: CPU sample 5.2 ms (기존 평균) + FP64 H2D p99 0.190 + M=5 커널 p99 1.271 + D2H p99 0.087 = 약 6.75 ms. 이 합은 가중평균, 준비, 최종 안전 처리, Python 호출과 pageable staging 등을 빠뜨린다.

- K=16,384: CPU sample 18.0 ms (8,192의 9.0 ms를 2배한 단순 외삽; 실측 아님) + FP64 H2D p99 0.648 + M=5 커널 p99 3.114 + D2H p99 0.061 = 약 21.82 ms. 이 합은 가중평균, 준비, 최종 안전 처리, Python 호출과 pageable staging 등을 빠뜨린다.

B는 남은 구간과 실제 커널을 계측해야 한다. C의 CPU 외삽치만으로도 예산을 넘으므로 S2의 GPU 후보 생성과 가중합이 필요할 가능성이 높다. CPU 16,384 실측이나 S2 전체 측정 없이 불가능하다고 확정하지 않는다. 이 시제품에서 FP64는 FP32보다 훨씬 느리므로 실제 S1이 시간 기준을 넘으면 FP32 정확도 검토가 타당하다. 정밀도 교체는 안전성 검증을 통과해야 한다.

## 개정 설계: S1 → S2

| 구분 | CPU | GPU | 경계 |
|---|---|---|---|
| S1 | `node.control_cb`의 상태 확인, 그룹·PP, 난수 및 후보 생성; 비용 수신 후 가중평균; 최종 단일 궤적 및 TTC·shield·명령 발행 | 후보별 ST rollout, 16점 투영 및 활성 비용 합산 | 연속 NumPy `(K,30,2)`·상태·트랙·장애물·그룹 등 입력 → `(K,)` 비용 |
| S2 | 상태·그룹·PP 및 최종 안전 처리 | 난수 상태, 매듭·보간·후보, rollout·비용, softmax·가중합 | 작은 상태·장애물·그룹·PP 입력 → `(30,2)` 명령열과 진단값 |

기존 코드상 `control_cb`에서 상태를 확인하고 `MPPI.step`을 호출한다. S1에서 `step`의 `mark('sample_ms')` 이후 기존 `_rollout`과 `_stage_costs` 및 smoothness 합산을 GPU 호출로 대체하고, 반환한 비용으로 기존 `weights`/`tensordot`를 실행한다. 최종 단일 롤아웃과 shield는 CPU에 둔다. 트랙 데이터는 초기 GPU 상주, 장애물·상태·그룹은 매 주기 갱신한다. K별 후보당 한 스레드, 시간 순차와 투영 힌트 의존성 보존을 시작안으로 삼는다.

| 비용 및 기능 | 이식 판단 |
|---|---|
| 횡·헤딩 추종, 속도, 횡가속, 트랙 경계 | 기준 설정에서 활성; 투영과 함께 GPU 이식 |
| 장애물 간격·충돌·근접과 TTC | 장애물 조건에서 활성; 이동·랩 경계·차체·무한 TTC까지 이식 |
| 입력 평활화 | 활성; `prev_u` 및 합산 순서 보존 |
| terminal, wall hit, side preference 등 기준에서 꺼진 항 | 실제 설정 검증 후 미지원 활성 옵션은 시작 거부 또는 별도 검증된 전체 CPU 설정을 명시적으로 선택. 조용히 생략하지 않는다 |
| 최종 단일 궤적, shield | CPU에 유지; 후보 전체를 CPU로 복사해 일부 비용만 처리하는 폴백은 대량 전송 위험 |

기준 설정은 기존 보고서에서 분석한 복사본 기준이며 실제 launch/ROS 덮어쓰기는 별도 확인한다. 활성 항 전체의 입력과 출력, 경계값, NaN/inf, 각 항 합산 순서를 검증한다. FMA·삼각함수·합산 순서로 FP64 1e-9 통과도 보장되지 않는다.

## 파일, 빌드, 호출과 안전

| 구성 | 제안 |
|---|---|
| `mppi_gpu.cu` | `extern "C"` ABI, 고정 dtype별 커널, 명시적 오류 코드, GPU 버퍼·스트림 관리 |
| 빌드 스크립트 | 컨테이너 nvcc 12.4로 `.so` 생성; `sm_86`, `sm_89` cubin과 `compute_89` PTX 포함. 이번 시제품은 두 cubin을 `cuobjdump`로 확인. 실제 4090 로드 검증은 필요 |
| `mppi_gpu.py` | `ctypes.CDLL`, `argtypes/restype` 명시; C 연속성과 dtype·shape·유한값·크기를 검사하고 `ndarray.ctypes.data` 포인터 전달; CPU 출력 및 장치 버퍼를 초기 할당 후 재사용 |
| 빌드 시점 | 이미지에 nvcc가 있다면 `install_final_demo.sh`에서 시작 전 빌드하는 방안. 해당 설치 스크립트와 평가 PC 권한·경로·nvcc는 확인 후 변경하며, 없으면 명시적 빌드 오류. 기존 진입점과 이미지 이름은 유지 |
| 초기화 | GPU, 아키텍처, 런타임 호환성, 메모리·설정 확인; 사용 K·dtype·M 경로에 대해 시작 전 load/warmup 및 결과 검사. 할당은 주기 밖 |
| 동기화/스레드 | 단일 소유 인스턴스와 락 또는 전용 스트림, NumPy 버퍼 수명 유지. 비동기 복사 완료 전 수정·해제 금지. 결과 사용 전 CUDA 이벤트/스트림 동기화, 호출별 공유 상태 경합 금지 |
| 오류/마감 | CUDA 오류·결과 비유한·워밍업 실패 시 시작하지 않음. 실행 중 오류나 마감 초과는 검증된 정지 경로 제안. 무한 대기 방지와 watchdog은 별도 설계·검증 필요. 자동 CPU 전환 금지 |

고정 버퍼는 최대 K와 자료형에 맞춰 크기를 검사한다. pinned 버퍼에 NumPy 후보를 복사하는 CPU 비용을 포함해 전체 주기를 재측정해야 한다. `ctypes` 빈 함수 호출은 작았지만 실제 인자 검증·동기화·복사는 포함하지 않는다.

## 4090 재측정 절차

1. 기존 평가 컨테이너의 CUDA 접근과 `nvcc`, Python/NumPy를 확인한다. 설치 또는 Docker/WSL 재시작은 하지 않는다.
2. `tables/gpu_port_feasibility/`의 `prototype.cu`, `build.sh`, `measure.py`, `verify_prototype.py`를 컨테이너 내 별도 빈 작업 폴더에 복사한다.
3. 그 폴더에서 `sh build.sh`, `python3 verify_prototype.py`, `python3 measure.py --library ./libprototype.so --output results_4090.json --warmup 100 --iterations 1000 --ks 1024 4096 16384 65536` 순서로 실행한다. 원시 JSON, 빌드 시간과 라이브러리 크기, 드라이버·GPU 및 부하를 함께 보관한다.
4. 측정 실패 항목은 JSON `errors`에 남기고 나머지 항목을 계속한다. CUDA 컨텍스트/최초 커널 자체 실패 시 컴파일·로드·실행 단계와 오류를 남기고 중단한다.

이번 첫 빌드는 `/usr/bin/time` 부재로 실패했고 Python 표준 라이브러리의 `perf_counter`로 빌드 시간 측정 후 성공했다. 61개 측정 항목 모두 오류 없이 각 1,000개 원시값을 저장했다. JSON과 스크립트는 `tables/gpu_port_feasibility/`에 있으며 기존 실험 폴더와 원본 코드는 수정하지 않았다. 이 결과는 제어기 동등성·충돌 안전성·실제 주행 성능의 증거가 아니다.
